==============================================================================
  SCREEN-TO-CODE NAVIGATION GUIDE
==============================================================================

PURPOSE
-------
Map each logical screen / dialog in Oregon Trail v2.1 to its location in
the unpacked binary (`work/OREGON_UNPACKED.BIN`) and to the corresponding
.PAS unit in this rebuild.  This lets you study how MECC laid out
screen-driving text in the binary and how that maps to the rebuild's
architecture.

THREE FILES YOU'LL USE
----------------------
All in `work/` (generated by the extractor scripts on your machine):

  1. `strings_atlas.txt`     — every printable string in the binary,
                                in offset order.  ~840 entries.
                                Columns: offset / length / kind / text

  2. `screens_atlas.txt`     — same strings grouped by likely game
                                system (store, river, hunt, illness, ...).

  3. `screens_navigation.txt`— 31 labeled SCREEN_NAMES (MAIN_MENU,
                                STORE_GREETING, PACE_MENU, etc.),
                                each pointing at the offset where its
                                opener text lives.  Use this as your
                                starting index.

REGENERATING THE ATLAS
----------------------
If you change which strings count (adjust MIN_LEN, add new anchor
patterns), re-run on your own machine:

    cd work
    python extract_strings.py    # rebuilds strings_atlas + screens_atlas
    python build_navmap.py       # rebuilds screens_navigation

The atlas files come from YOUR OREGON_UNPACKED.BIN.

HOW TO READ A .PAS UNIT
-----------------------
Each unit header in `src/` now ends with an "Original screen-text
positions" block listing the offsets it corresponds to.  Example
(from STORE.PAS):

    Original screen-text positions in OREGON_UNPACKED.BIN:
      STORE_GREETING          @ 0x0DB7D  (Matt intro)
      STORE_GREETING          @ 0x0DB46  (sales pitch)
      STORE_ITEMS / banner    @ 0x0E793
      STORE_LIMIT_OXEN        @ 0x09583, 0x0DECB
      STORE_LIMIT_FOOD        @ 0x0959E
      "You may buy:" header   @ 0x09886

When you want to see what the original text says:

    1. Open work/strings_atlas.txt
    2. Search for `0x0DB7D`
    3. Read the verbatim text on that line

The .PAS unit itself contains a clean-room rewrite of the prompts/menus
in my own words.  It implements the same MECHANICS but uses different
prose so the rebuild can be redistributed.  The "Original screen-text
positions" block lets you compare ARCHITECTURE without me being a
channel for verbatim prose.

WHAT TO LEARN FROM THE LAYOUT
-----------------------------
A few patterns worth noting once you start browsing offsets:

* Many screens cluster around 0x09000-0x0E000 (about 20 KB of game
  text in the middle of the data segment).  This is the "Tier 1"
  message pool -- frequently-referenced strings get the cheaper
  near-pointer addressing.

* The "DAILY_MENU" header at 0x03DD6 is one of three strings tagged
  in the navigation map.  All three actually look up to the SAME
  offset because the daily-menu text is one long block that prints
  multiple visible screens (check supplies / map / rest / pace /
  ration / talk are all sub-options dispatched off the same body
  string).  This tells you the original handles them as ONE menu
  state with sub-cases, not separate screens -- different from how
  my TRAVEL.PAS splits ChangePace / ChangeRation into separate
  procedures.

* Tombstone, victory, and copy-protect strings sit far apart
  (0x12975, 0x07CA5, 0x1580B).  Endgame paths are distinct code paths,
  not folded into a single "finalize" function.

* Several "PRESS SPACE BAR" prompts repeat at 0x089D0, 0x0E843, 0x23AE4.
  This is because the original copies the same prompt into several
  segment-local string tables (hunting, store, generic).  The rebuild
  uses one shared message; the original duplicates for locality.
